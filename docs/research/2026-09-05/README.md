# TAP to PICK — 모바일 게임 수정 과정 기록

작성일: 2026-09-05 · 기록 기준: [`1b8b69f`](https://github.com/Junyyyong/TaptoPick/commit/1b8b69f)

## 기록 목적과 읽는 방법

개발 중 제기된 문제와 디자인 요청을 **문제 → 수정 → 화면 → 확인 결과** 순서로 정리했다. 문제 설명은 개발 대화의 요약이며, 사용자 조사나 실험에서 수집한 원문 인용이 아니다. 화면은 당시 촬영해 두었던 사진이 아니라, **Git에 남아 있는 해당 버전을 이번 기록 작업에서 다시 실행한 재현 스크린샷**이다.

모든 화면은 세로형 모바일 환경인 **390 × 844 CSS px**, 배율 2에서 캡처했다. 원본 PNG는 **780 × 1688 px**이며 아래에서는 읽기 편하게 축소 표시한다. 원본은 [screenshots 폴더](screenshots)에 있다. 실제 휴대폰 촬영이나 모든 기종에 대한 호환성 검증은 아니다.

기록의 핵심은 변경의 추적 가능성이다. “더 쉬워졌다”, “더 빨라졌다”는 개발 의도와 실제 검증 결과를 구분했다. 난이도·만족도·로딩 시간에 대한 사용자 실험은 이 작업에 포함하지 않았다.

## 1. 원본 게임 구조를 이미지 찾기 게임으로 전환

**요구:** TAPtoTALK의 구조·디자인·폰트를 계승하되, 원본 게임을 건드리지 않고 별도 게임을 제작한다.

**수정:** TaptoPick 저장소에 복사된 기준 버전에서 세 가지 이미지 게임을 구성했다. 첫 번째는 전체 그림에 속한 조각 찾기, 두 번째는 제시 그림과 같은 그림 찾기, 세 번째는 카드 페어 찾기다. 조각 번호는 왼쪽 위부터 행 순서로 3×3 또는 3×4에 대응하도록 정리했다.

## 5. 이미지 최적화 — 파일 용량을 근거로 기록

**문제:** 게임 진입 후 이미지가 늦게 나타난다는 개발 중 관찰이 있었다. 원본 PNG·JPG를 게임 표시 크기에 맞는 자산으로 정리할 필요가 있었다.

**수정:** 웹용 WebP 자산을 생성해 사용하고, 이후 시작 화면에서 게임 이미지를 미리 준비하는 처리를 추가했다(`444fd07`, `55c12be`).

| 동일 이름으로 대응되는 조각 75개 | Git 파일 크기 합계 |
|---|---:|
| 변경 전 JPG (`219b041`) | 2,941,708 bytes |
| 변경 후 WebP (`444fd07`) | 199,118 bytes |
| 감소량 | 2,742,590 bytes, 약 **93.2% 감소** |

**확인:** 75개 파일의 이름 대응과 저장된 파일 크기를 Git 객체에서 확인했다. 원자료는 [git-evidence.json](git-evidence.json)의 `picturePieces`에 있다. 이는 **해당 조각 자산의 용량 비교**이지 전체 앱 크기, 모든 게임 이미지의 압축률, 다운로드 전송량 또는 로딩 시간 측정치가 아니다. 따라서 “93.2% 더 빨라졌다”고 해석해서는 안 된다. 실제 속도 검증에는 동일 기기·네트워크의 캐시 유무별 측정이 추가로 필요하다.

## 7. 게임 2 — 임의 시각 변형에서 제공된 정답·오답 자산으로

**문제:** 회전·색·크기 변화만으로는 원하는 세부 형태 차이를 만들기 어려웠고, 전신 차이는 모바일에서 잘 보이지 않았다. 같은 캐릭터가 자주 반복되어 일곱 캐릭터를 모두 경험하기도 어려웠다.

**수정:** 제공된 얼굴 정답과 바리에이션 이미지를 콘텐츠로 등록했다. 해피부터 시작해 뽀글스, 티피·태피, 후피·재피·피노팬까지 확대했다. 일곱 캐릭터를 한 번씩 소진한 뒤 다시 섞는 방식으로 변경했다. 점수 표시는 누적 점수 대신 찾은 개수로 바꿨다.

|---|---|
| <img src="screenshots/13-face-montage.png" width="260" alt="해피 얼굴 콘텐츠 도입"> | <img src="screenshots/14-seven-member-content.png" width="260" alt="일곱 캐릭터 등록 버전에서 재현한 해피 문제"> |
| `d86d1af` | `2d1c636` |

**확인:** 두 캡처는 모두 해피 문제다. 화면 한 장으로 일곱 캐릭터의 등록·순서를 증명하지 않는다. 콘텐츠 확대는 `16eec6a`, `c240696`, `2d1c636`, 순환 출제는 `fa3c2bf`, 개수 표시는 `a4c7d51`의 코드 이력이 근거다. 오답은 제공된 바리에이션이며 중복 배치가 허용된다.

## 8. 게임 3 — 작은 조각 49개에서 얼굴 페어로 단순화

**수정:** 카드 뒷면을 여러 색으로 바꾸고, 조각 대신 얼굴을 찾는 방식으로 전환했다. 이후 바리에이션까지 기억해야 하는 부담을 줄이기 위해 **일곱 캐릭터의 원본 얼굴만** 사용하도록 제한했다. 동일 원본이 여러 쌍 나오는 것은 허용한다. 별도로 업로드한 게임 3 표정 자산은 보류했다.

## 9. 게임 3 — 한 판을 네 단계로 구성

**요구:** 작은 보드부터 시작해 7×7까지 진행하되, 큰 단계에는 시간을 더 준다.

## 10. 카드가 직사각형으로 나타나거나 클릭 때 크기가 변하는 문제

## 근거 파일과 재현 방법

- [manifest.json](manifest.json): 34개 캡처의 커밋 SHA, 커밋 시각, 시나리오, 이미지 경로·해시, 화면 상태, 브라우저 정보.
- [git-evidence.json](git-evidence.json): 기준 버전까지의 커밋 목록과 이미지 용량 비교 원자료.
- [capture.cjs](capture.cjs): 모바일 캡처 재현 스크립트.
- [evidence.cjs](evidence.cjs): Git 파일 크기·이력 추출 스크립트.
- [verify.cjs](verify.cjs): 이미지 크기·해시·문서 참조와 캡처 오류 검사.
- [verification.json](verification.json): 위 검사 결과.

재현에는 저장소의 Git 이력, 기존 개발 의존성, Node.js, Playwright, Chrome이 필요하다. Playwright는 기록 도구용 외부 설치를 사용했으며 게임의 package.json에는 추가하지 않았다.

```sh
NODE_PATH=/path/to/node_modules CHROME_PATH=/path/to/chrome node docs/research/2026-09-05/capture.cjs
node docs/research/2026-09-05/evidence.cjs
node docs/research/2026-09-05/verify.cjs
```

`RESEARCH_REFS=1b8b69f`처럼 지정하면 선택한 버전만 다시 캡처할 수 있다. 스크립트는 Git 스냅샷을 새 임시 폴더에 내보내고 로컬 Vite 서버에서 실행한다. 현재 작업 브랜치를 과거 버전으로 돌리지 않는다. 로컬 자산을 불러온 뒤 캡처하며, 난수 시드를 고정하고 브라우저 시계를 제어해 원하는 애니메이션 프레임을 재현한다. 따라서 프레임의 시간 값은 실제 플레이어가 소요한 시간이 아니다.

### 연구 자료로 사용할 때의 한계

1. 커밋이 없는 중간 상태는 임의로 만들어 전·후 화면으로 제시하지 않았다. 한 커밋에 여러 수정이 포함된 경우에는 한 가지 수정만의 효과를 분리할 수 없다.
2. 같은 화면 구성 비교라도 버전별 캐릭터·난수 소비 방식이 달라 대상 이미지가 다를 수 있다. 엄밀한 동일 자극 실험 자료가 아니다.
3. 캡처는 이미지 로딩 완료 후의 재현 화면이다. 초기 로딩 지연·순간 레이아웃 흔들림을 정지 화면으로 입증하지 못한 부분은 별도 표시했다.
4. 사용자 난이도, 실패율, 만족도, 로딩 속도는 별도 측정해야 한다. 후속 연구에서는 기기·브라우저·네트워크·캐시 상태, 성공률, 오답 수, 완료 시간, 참가자 수를 함께 기록하면 좋다.

### 게임에 미치는 영향

이번 기록 작업의 추가 파일은 **docs/research/** 안에만 둔다. 게임 소스·규칙·원본 이미지·의존성은 수정하지 않는다. 앱에서 이 문서를 불러오지 않으며 일반 게임 빌드에 스크린샷을 포함하지 않는다. Git에 올리면 저장소 용량은 늘지만 게임 다운로드용 자산에 자동으로 추가되는 것은 아니다. 원본 **Junyyyong/TAPtoTALK** 저장소는 수정하지 않는다.

기록 작성 후 `npm run build`가 성공했으며, `npm test -- src/core/pick src/content/puzzles.test.ts`의 **4개 파일, 36개 테스트가 통과**했다. 문서 검사에서는 34개 PNG의 크기·해시·참조 경로, 캡처 중 페이지 오류 없음, 표시 이미지 로딩 완료를 확인했다. 스크린샷 원본의 합계 크기는 약 25.7 MB이며, 일반 빌드 결과에 연구 기록 파일이 들어가지 않는 것도 확인했다.
